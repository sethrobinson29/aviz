# Music Visualizer — Design Spec

## 1. Goals

- Real-time audio-reactive visualizer with a layered, compositable system.
- Support both local audio files and "any source" playback (browser tabs, streaming apps) via system audio loopback rather than fragile per-service integrations.
- Users can stack multiple visual layers, each independently configurable and independently audio-reactive.

## 2. Tech Stack

| Concern | Choice | Why |
|---|---|---|
| Language (core) | C++17 | Agent-friendly, single language for audio/visual core, no FFI boundaries within it |
| Audio I/O + loopback | miniaudio | Single-header, wraps WASAPI / Core Audio / PulseAudio-PipeWire loopback behind one API |
| Rendering | raylib | Simple immediate-mode graphics, easy to target for waveform/spectrum/particle visuals |
| FFT | pffft (`marton78/pffft`, v1.1.0) | Real-valued FFT support + SIMD (SSE) optimization on the hot audio-processing path; float precision, SSE only — see `STRUCTURE.md`'s dependency policy for full rationale |
| Control panel UI | WebView2 (HTML/CSS/JS) | Native Windows webview embed; needed to hit real Y2K/Frutiger-Aero visual fidelity (gradients, glass/blur, chrome) — see §7 |

Rejected: Rust + cpal — loopback/capture support is thinner and less battle-tested than miniaudio; would likely require dropping to raw platform APIs anyway.

Note: the control panel UI is a deliberate exception to the "one language, no FFI" principle for the audio/visual core — see §7 for the rationale and the interface boundary (`UIHost`) that contains that exception.

## 3. Audio Input

Two producers feed the same downstream pipeline:

1. **Local file playback** — decode via miniaudio, fixed known sample rate. **`FileProducer` is pimpl'd, with a thin `miniaudio_backend.h` wrapper**, specifically because `miniaudio.h` pulls in `<windows.h>`, which collides with `raylib.h` if both are visible in the same translation unit. This is a real build constraint, not incidental structure — don't collapse the wrapper away "for simplicity" without checking this first.
2. **System loopback capture** — platform-specific, variable sample rate/buffer size:
   - Windows: WASAPI loopback mode
   - macOS: Core Audio process taps (macOS 14.4+) or BlackHole virtual device fallback; requires user consent (similar to screen-recording permission)
   - Linux: PipeWire / PulseAudio monitor source

**`LoopbackProducer` config sentinel values, non-obvious and easy to "correct" into a bug:** `pDeviceID = nullptr` means "use the default device," and `channels = 0` / `sampleRate = 0` mean "accept whatever the device's native format is" — these are miniaudio's own sentinel conventions, not placeholder/uninitialized values. Setting an explicit device ID or explicit channel/rate values where a sentinel is intended would silently change behavior (pin to a specific device, or reject the device's native format) rather than erroring.

Both producers push raw PCM frames into a shared ring buffer via a common interface (`push_frames(samples, count, channels, sample_rate)`), so the rest of the pipeline doesn't know or care which source it came from.

**Design implications:**
- FFT windowing must tolerate variable sample rates/buffer sizes (loopback), not assume a fixed rate like local files provide.
- Loopback has a frame or two of inherent latency — beat detection and visual response should be designed with that slack in mind, since the app is a passive observer of someone else's playback pipeline.
- Explicitly out of scope: direct YouTube/Bandcamp stream extraction. YouTube's player is a sandboxed iframe with no exposed audio stream; Bandcamp's CORS/audio-analysis support is inconsistent and scraping stream URLs isn't an officially supported use. Loopback capture sidesteps both problems and works with any source without touching either site's ToS.

**Ring buffer overflow policy: overwrite-oldest.** If the feature-extraction worker falls behind the audio callback, new frames overwrite the oldest unread frames rather than being rejected. This bounds latency so visuals track live audio rather than drifting further behind under sustained load, which matters more for perceived responsiveness in a real-time visualizer than strict analytical completeness (a reject-new policy would guarantee no frames are skipped, at the cost of unbounded latency growth if the worker can't keep up). Two known tradeoffs of this choice, both accepted:
- A skipped chunk containing a transient means that transient is never seen by onset detection — a possible missed beat under sustained worker overload, rather than a delayed one.
- When the worker's read pointer jumps forward past overwritten frames, the next analysis window is no longer temporally contiguous with the last one processed. Since onset detection is spectral-flux-based (frame-to-frame energy delta), a discontinuity like this can look like a transient and fire a spurious onset. Mitigation: the producer sets a discontinuity flag when an overwrite occurs, so the worker resets its onset-detection history on the next window instead of comparing across the gap as if it were contiguous.

**Ring buffer capacity must be a power of two.** `AudioRingBuffer::capacity_frames` relies on this for cheap index wraparound (bitmask, not modulo) — only debug-asserted, silently trusted in release builds. Found while removing a comment that was the only place this requirement was recorded; not otherwise enforced or visible at the call site. Don't construct the ring buffer with a non-power-of-two capacity.

**Lifetime contracts, not currently enforced by any type — violating them is undefined behavior, not a caught error.** The ring buffer must outlive any producer's `stop()` call (a producer's data callback may still reference it up until `stop()`'s synchronous join completes, per the `ProducerHost` guarantee above). The ring buffer and the `AudioFeatures` triple-buffer snapshot must both outlive `FeatureWorker` (the worker thread reads from one and writes the other for its entire lifetime). These are ownership/destruction-order requirements on whoever constructs and wires up the audio pipeline (`app.cpp`) — get the order wrong and the failure is a use-after-free, not a clean error.

**Worker signaling: fixed-interval polling.** The feature-extraction worker polls for new PCM on a fixed interval rather than being signaled via a condition variable on push. The interval is chosen based on the smallest expected FFT window/hop size (§4), so the worst-case added latency from polling is bounded and known rather than incidental — not an arbitrary round number.

**Canonical pipeline format (milestone 5): 48kHz, stereo, f32 — hardcoded, not queried at runtime.** Both `FileProducer` and `LoopbackProducer` convert their native output to this fixed format before `push_frames`, via a preallocated `ma_data_converter` per producer. This is what makes invariant #5 ("producers are interchangeable") actually true rather than aspirational: the ring buffer and `FeatureWorker` are created once at startup and never rebuilt, since they no longer need to care which producer is active or what that producer's native format is — switching producers is just stop/start, not teardown/recreate. This was chosen over a narrower "resample rate only, let channel count float" fix specifically because a floating channel count would still force ring-buffer/worker teardown on every source switch, re-introducing the discontinuity/reset behavior this milestone's canonicalization was meant to eliminate.

**Mid-session producer switching: `ProducerHost`, a structural gatekeeper, not a documented convention.** `app.cpp` never holds a raw producer pointer — only a `ProducerHost` (`src/audio/producer_host.h`), whose `switch_to(std::unique_ptr<AudioProducer> next)` is the only method that can change the active producer, and whose entire body is `current_->stop(); current_ = std::move(next); current_->start(ring_);`. There is no second public path capable of calling a producer's `start()`/`stop()` out of order — the ordering isn't a rule callers are expected to follow, it's the only thing this type's one mutating method does. `AudioProducer::stop()` carries an interface postcondition ("must not return until no further call to the producer's data callback can occur") that every implementation, present and future, must satisfy — not just an accident of how the current WASAPI-backed producers happen to behave.

This structural guarantee rests on a real, checked fact about the pinned miniaudio dependency, not an assumption: at the pinned tag (`v0.11.25`, per `STRUCTURE.md`'s dependency policy), WASAPI is classified non-asynchronous by miniaudio (registers `onDeviceRead`/`onDeviceWrite`, not `onDeviceDataLoop`), which means `ma_device_uninit()` performs a genuine synchronous join of the device thread before returning — `stop()` isn't just signaling intent, it's provably waiting for the callback thread to fully finish. As long as `switch_to()`'s sequential ordering holds (which it structurally must, being the only mutating path), there's no window for the outgoing and incoming producers to race on the ring buffer.

**Caveat worth carrying forward, not treating as settled forever: this is pinned-version-specific.** miniaudio's own source carries a `#if 0`'d-out block showing this synchronous-stop behavior has been implemented differently before, with a comment noting backend/OS sleep-state edge cases. A future bump of miniaudio's `GIT_TAG` should re-verify this classification against the new pinned source rather than assume it still holds.

**Verification note: TSan is structurally blind to this specific interaction.** WASAPI doesn't exist under WSL2, so the `tsan/` diagnostic build (§ concurrency, `TESTING.md`) can exercise the ring buffer/triple-buffer logic against synthetic producers but cannot exercise the real producer-switch path at all. This interaction is covered instead by an automated ordering test (`producer_host_test.cpp`, GoogleMock asserting `stop()` is called before `start()`) plus real rapid-toggle stress testing on the actual Windows machine (100+ switches, varied timing, several minutes, watching for hangs/crashes/stale frames/resource growth) — not a single manual toggle, consistent with this project's established distrust of "seemed to work once" as sufficient evidence for concurrency-adjacent claims.

Reasoning for each part of the format, since none of the three is arbitrary:
- **48kHz** — WASAPI shared-mode loopback negotiates to Windows' audio-engine mix rate, which defaults to 48kHz on most machines, so loopback typically needs zero rate conversion in practice — only the file-playback path actually resamples. Also matches every worked example already in §4 (window/hop timing, Hz/bin resolution), making those numbers exact rather than approximate.
- **f32** — already the only format miniaudio and this codebase use anywhere (`FileProducer` already decodes to `ma_format_f32`, the ring buffer stores `atomic<float>`); not a new choice, just not introducing a second format.
- **Stereo** — enables Lissajous (§6, stereo L/R plotting, built at milestone 6, real separation verified end-to-end) at zero pipeline cost, since both producers are naturally stereo anyway. `AudioFeatures.waveform` is mixed down to mono downstream inside `FeatureWorker` for every other visual; canonicalizing to mono at the pipeline level instead would have forced a second migration when Lissajous needed real channel separation, which it now does.

**Deliberately hardcoded, not dynamic — a known, cheap thing to revisit if ever needed, not an oversight.** 48kHz is a compile-time constant, not queried from the system's actual mix rate at startup. This is a real, if narrow, machine-dependent behavior: on a machine whose WASAPI mix rate isn't 48kHz, loopback would need real, always-on resampling rather than the typical zero-conversion case described above — a path that won't be exercised or verified by testing on a single dev machine. Kept hardcoded anyway because this project isn't currently run anywhere but one machine, and querying the rate dynamically is a small, well-scoped change if that ever stops being true: read the native rate once at startup via miniaudio/WASAPI's device-info query, store it instead of the constant, pass it into both producers' converter setup — no changes needed anywhere downstream (FFT, banding, onset detection, AGC), since none of that hardcodes 48kHz as a literal, it all derives from whatever `sample_rate` it's handed. The one real cost: §4's worked numbers (window duration, Hz/bin resolution, update rate) would stop being exact and become rate-dependent.

## 4. Feature Extraction (shared, computed once per frame)

All visuals consume the same computed feature set — never raw samples directly.

- **Banded spectrum**: FFT output binned into ~8–32 log-scaled bands (sub-bass through presence/air), plus presets like bass/low-mid/high-mid/treble or a simpler bass/mid/treble/full, with raw Hz ranges editable underneath.

  **Concrete layout: 16 log-scaled bands + 1 global band = 17 total, fixed-size (`std::array`, no per-frame allocation).** 16 was chosen as a middle of the spec's 8–32 range, divides evenly into 4-band preset groupings (bass/low-mid/high-mid/treble) with no remainder, and is enough granularity for band-mapped layers to feel distinct without carrying 32 bands' worth of onset-detection history state for marginal benefit. The global band sits at the **last index** (`kGlobalBandIndex = kNumBands = 16`), not prepended or interleaved — this keeps the log-scaled bands at indices `0..15` contiguous and trivially iterable (`for (i = 0; i < kNumBands; i++)`) for anything sweeping "all real frequency bands" (spectrum visual, preset grouping, UI band list), since global is an aggregate, not a point on the log-frequency sweep, and gets its own named constant instead. `kTotalBands = kNumBands + 1 = 17`.

  **Band-edge-to-bin mapping: running cursor, not independent per-band rounding — fixes a real bug, not a hypothetical.** Found via visual testing (unpredictable smearing on the low end) rather than by the original unit tests: rounding each band's edges to FFT bins independently let adjacent low-frequency bands round to the *same* bin at the ~46.9 Hz/bin resolution (§4's window/hop decision), since log-spaced band edges are closer together than the linear bin resolution down there. Two bands both reading the same bin isn't just coarse data, it's aliasing — data bleeding across a band boundary that's supposed to be a clean separation. Fixed with a running bin cursor: each band's start bin is forced to be the previous band's end (`bin_hi = min(max(bin_for(edge_hi), bin_cursor + 1), kNumFftBins)`), guaranteeing a contiguous, non-overlapping partition of the spectrum with every band getting at least one bin. This is watertight for the current constants (`kNumBands = 16` vs. `kNumFftBins = 513`, nowhere close to the margin where the trailing clamp could produce a zero-width band) but isn't a universal invariant independent of them — a debug-build assert on both ends of the guarantee (every band's `bin_end > bin_begin`, and the final band's `bin_end` doesn't exceed `kNumFftBins`) makes this self-checking rather than something that has to be re-derived by hand if the band count or FFT size ever changes (band count changing at all requires discussion per `CLAUDE.md` invariant #3, but the assert costs nothing in release builds and this is the second bug found at this exact low-end coarse-resolution boundary — worth the cheap defense).
- **Per-band onset/beat detection**: spectral-flux-style (frame-to-frame energy increase, peak-picked above a rolling threshold), computed independently per band. A kick-drum transient in the sub-bass band and a hi-hat/snare transient in the 2–5kHz band trigger differently, which is what makes band-mapped layers feel distinct rather than just synced pulses.

  **Concrete threshold: `threshold[n] = max(mean(flux, trailing window) + k·stddev(flux, trailing window), absolute_floor)`.** Trailing window ~92 frames (~1 sec at hop 512/48kHz), `k` ~1.5–2.0, refractory period ~50–100ms minimum inter-onset time to prevent a single transient's decay from double-firing — all tunable constants per the requirement below. Maintained incrementally (running sum/sum-of-squares over a circular buffer, O(1) per update) rather than via a true rolling median, since this runs per-band (17 bands) every hop and the performance-priority guideline (`CLAUDE.md`) favors it; median's extra robustness to outliers isn't needed here.

  **`absolute_floor = 0.1f`, tunable — added to fix a real robustness bug, not a hypothetical.** With an all-zero flux history (true silence, no noise floor), the adaptive term alone (`mean + k·stddev`) collapses to exactly 0, so the *first* nonzero flux value in that band — however tiny — fired an onset regardless of whether it was a real transient. This caused every band to fire simultaneously right at a track's true first onset, since the same collapse happened everywhere at once. A relative-only threshold can't self-correct for this: the floor has to be an absolute value independent of the trailing window's own statistics. Found by real listening + live debug output, not by an existing test — worth remembering this class of bug (threshold math degenerate at a boundary condition) isn't something the original synthetic fixtures happened to cover.

  **Implementation had drifted from this design — found and fixed via a code comment audit, not a functional test.** The shipped code computed `mean + k·stddev + epsilon` (a permanent additive term, applied unconditionally on every hop) rather than `max(mean + k·stddev, absolute_floor)` (a clamp, inert except when the adaptive term is already at or below the floor). These aren't equivalent outside the near-silence case both were meant to fix: the additive version permanently reduced onset sensitivity across all normal listening, not just quiet passages, for no documented reason. This wasn't drift from a working state — it was implemented this way from the original commit, alongside `has_baseline` (below), and the divergence from spec went unnoticed until an unrelated comment-cleanup pass forced a line-by-line re-read of the formula against this section. Fixed to match the `max()` clamp design above, using the floor value already specified here (`0.1f`); verified with both new unit tests (clamp boundary behavior) and a human re-listen against milestone 1/2 test material, since removing the permanent additive term is a real sensitivity change on real audio, not just a math correction (per `TESTING.md`'s audio correctness section — clean unit tests alone don't cover this class of change).

  **Cold-start guard (`has_baseline`): a separate, real mechanism, not a duplicate of the floor.** For the first ~`kOnsetHistoryLength` hops of a file (or after `reset_onset_history()` following a ring-buffer discontinuity), the trailing window doesn't yet have enough samples for `mean`/`stddev` to be numerically reliable — even with the floor in place, a threshold computed from a near-empty window could behave unpredictably in ways a floor alone doesn't fully guard against. `has_baseline` suppresses onset detection entirely until a full trailing window exists, rather than trusting statistics computed from too little data. This is complementary to the floor, not redundant with it: the floor protects ongoing near-silence anywhere in a track; `has_baseline` protects specifically against unreliable early statistics at startup or after a reset. Both are kept.

  **`reset_onset_history()` must never touch AGC state.** A ring-buffer discontinuity resets onset-detection history (per §3's discontinuity mitigation) but must leave `agc_reference_`/`agc_seeded_` untouched. These are unrelated concerns that happen to be adjacent in the same worker: onset history is about detecting transients correctly across a data discontinuity, while the AGC reference is a slow-decay peak-hold specifically designed to survive gaps and hold its ceiling (§4 below) — resetting it on every discontinuity would defeat the entire point of it being slow-decay. Losing this separation on a future edit (e.g. a well-intentioned "reset everything on discontinuity" refactor) would silently reintroduce AGC instability without an obvious symptom pointing back to the cause.
- **Global beat detection**: implemented as a degenerate case of the same per-band computation, with the band scoped to full-spectrum energy — not a separate detection system. Gives layers a consistent "master clock" to lock onto without requiring a second algorithm.
- **RMS/volume** and **peak frequency** as simple scalar features.

Struct shape (conceptual): a per-frame snapshot containing raw recent waveform samples (mono `waveform`, plus separated `waveform_l`/`waveform_r` for Lissajous — §6), an array of band energies + onsets (including the full-spectrum/global band), a per-band idle classification (`band_idle`, read-only derived state — see below), RMS, and peak frequency — handed to every active layer each frame.

**Publishing mechanism: triple buffering, not a 2-slot double-buffer.** Three preallocated `AudioFeatures` instances: the worker thread exclusively owns a private back slot (writes new results into it), the render thread exclusively owns a private front slot (reads from it), and a third shared middle slot changes ownership between them. This took two structural iterations to get right, not one — see `TESTING.md`'s track record note for the full sequence. The shipped mechanism: the slot index and a new-data flag are packed into a single atomic word (not two separate atomics), and the consumer side claims the shared slot via a **compare-exchange retry loop**, not a blind atomic exchange — a blind exchange on the consumer side is exactly what caused the second regression, since it let the consumer briefly hold a slot the producer still believed it owned. This was not the first design — a simpler 2-slot double-buffer with an atomic index/pointer was tried first and found to have a genuine data race: since the worker must never block (`CLAUDE.md` invariant #1), nothing bounds how many times it can publish while the render thread is still mid-read (a multi-statement read, e.g. `f.rms` then `f.band_energy[...]`) of the slot it's holding a reference to, so the worker can wrap back into that exact slot while it's still being read. Triple buffering with the packed-word/CAS handoff removes this structurally: ownership transfer is atomic and contested correctly, so a reader either has exclusive access to a complete, consistent front slot or it doesn't — there's no partial-overwrite window. Worst case under adversarial timing is the render thread reusing one stale frame for an extra cycle, which is benign (same tolerate-staleness-over-corruption spirit as the ring buffer's discontinuity flag), not a torn/inconsistent read.

**FFT window/hop size: 1024/512.** At 48kHz — the canonical pipeline sample rate as of milestone 5 (§3), hardcoded, not just a typical assumption — this gives ~21.3ms windows, ~46.9 Hz/bin frequency resolution, and an update rate (~93/sec) comfortably above display refresh (60fps) — no visible stepping in feature values across render frames. Chosen as a middle ground between 512/256 (finer timing, coarser frequency resolution) and 2048/1024 (finer frequency resolution, more added latency, update rate close enough to 60fps to risk visible stepping). These numbers are exact at 48kHz, not approximate — if the canonical rate is ever made dynamic (querying the actual system mix rate instead of hardcoding) they'd shift slightly and become rate-dependent rather than fixed. Hardcoding now was a deliberate choice, not an oversight — see §3's canonical format note for why, and for what changing it later would actually involve.

**Window size, hop size, band boundaries, and envelope attack/release constants must all be tunable** — named constants or a small config struct in the audio/feature-extraction code, not literals scattered through the FFT/banding logic. This project is expected to need by-ear/by-eye tuning once it's actually running, independent of any future shipping ambitions; hardcoding these values would mean a recompile for every experiment.

**Envelope smoothing (resolves the §9 gap): asymmetric one-pole IIR, separate attack/release coefficients.** `env[n] = coeff·env[n-1] + (1-coeff)·value`, where `coeff` switches between an attack coefficient when the input is rising and a release coefficient when falling, each derived from a target time constant via `coeff = exp(-hop_time / tau)`. Starting values: attack `tau` ~10–20ms (responsive to a transient), release `tau` ~150–300ms (avoids flicker, gives a felt decay rather than a hard cutoff). Applied to `band_energy` before it's ever handed to a visual layer. Both time constants are tunable per the requirement above.

**No-signal idle state (resolves the §9 gap): reuses the envelope, per-band relative floor, no hard-zero assignment.** When audio pauses or a source (or a single band) goes genuinely quiet, visuals fade to a flat/rest appearance rather than snapping — but this isn't a separate mechanism layered on top of the envelope, it's a read-only classification derived from it.

**Real implementation bug found and fixed, not just a design gap.** This design was specified correctly from the start — gate on the per-band smoothed value, not raw RMS — but what originally shipped in `WaveformVisual::render()` and `SpectrumVisual::render()` gated on **whole-mix `features.rms`** instead, exactly the mistake this section already warned against. Confirmed via traced per-hop logging (raw signal → FFT/banding → envelope → AGC/ratio, each layer individually verified clean before finding the actual fault at the render-gating step): a band's `ratio` stayed smooth and continuous throughout a quiet passage while `normalized`/rendered height snapped to exactly 0 whenever whole-mix RMS happened to dip under a fixed threshold — discarding a real, correctly-computed value because of an unrelated aggregate signal. This produced "rise, disappear, rise" rather than "rise, decay, settle low," uniformly across every band and reactivity mode, since the gate was applied identically regardless of which band or mode a layer was using.

**First fix attempt (insufficient on its own):** replaced the whole-mix gate with a single fixed per-band epsilon (`smoothed_energy_[band] < kIdleFloorEpsilon`, comparing against an absolute constant). This fixed the original bug but reproduced its same *shape* in miniature: high/treble bands, whose typical energy scale is naturally smaller than bass/low-mid bands, were incorrectly classified idle by a threshold tuned for lower bands' scale — the same "single constant miscalibrated for bands with different typical magnitudes" pattern as the AGC investigation's original bug (§4, AGC bug 1).

**Final mechanism, as shipped:** `out.band_idle[band] = smoothed_energy_[band] < kIdleFloorFraction * agc_reference_[band]` (`kIdleFloorFraction = 0.02f`, `src/audio/audio_config.h`) — the floor scales with each band's own AGC reference rather than being one absolute value, directly solving the treble-band misclassification. This comparison is placed **after** that hop's AGC reference rise/decay update and its own floor clamp — reading the just-updated reference, not the previous hop's stale value. This ordering is a hard requirement, not incidental: comparing against a stale reference would reproduce the exact staleness-bug shape already found and fixed once for the ratio computation itself (§4, AGC bug 5). Verified directly via a mutation test (temporarily moving the comparison before the reference update, confirming the test fails, then reverting) rather than assumed correct from the code's structure.

**`band_idle` is purely a read-only classification — it never assigns anything.** An earlier iteration of this fix set `smoothed_energy_[band] = 0.0f` outright once classified idle, which produced a visible one-hop discontinuity (a smooth decay curve jumping straight to zero rather than continuing to approach it asymptotically). That hard assignment was removed entirely: `smoothed_energy_[band]` is now only ever touched by its own attack/release envelope math, decaying naturally under the same curve it always used, and `band_idle` is a derived boolean a visual can read without the underlying value ever being stomped.

**Cosmetic minimum bar height, separate concern:** `kMinBarHeightPx = 4.0f` (`src/visuals/visual_config.h`, untuned starting value) is a pixel-level floor applied strictly at the last step of rendering (`std::max(normalized * max_height, kMinBarHeightPx)`), after idle classification, AGC ratio, sensitivity, and clamping are all fully resolved. Nothing upstream reads or branches on this value — it exists purely so bars remain faintly visible rather than fully vanishing, and is unrelated to the idle-detection mechanism itself.

This is shared across all visuals reading `AudioFeatures` — no per-visual-type idle logic needed.

**Per-band AGC reference (normalizes `band_energy` for bar-style display; found via visual testing, four real bugs deep):** spectrum-style visuals need each band's energy normalized against "what's typical for this band" to produce a sensible bar height. A single global reference constant was tried first and rejected — see below — in favor of a per-band adaptive peak-hold reference, a second, independent one-pole filter per band alongside the existing fast display envelope.

*Design, as currently settled:*
- **Two independent filters per band, not one doing double duty:** the existing fast attack/slow release display envelope (above) drives what's shown; a separate, slower AGC reference tracks a peak-hold ceiling used only for normalization. Mixing the two into one filter was explicitly avoided.
- **Fed from `smoothed_energy_` (the same value being displayed), not raw energy.** This is load-bearing, not a style preference — see bug 2 below.
- **Asymmetric peak-hold shape: instant-snap rise, slow decay.** Rise is an unconditional `reference = max(reference, current_value)` each hop — no blending, no tau — so a genuine new peak is captured immediately regardless of how briefly the signal is above the previous reference. Decay is a slow one-pole release, giving the reference a "ceiling that holds" character rather than one that just chases the current level. (Standard, established design for peak-hold meters generally, not novel to this project.)
- **Ratio computed only after the current hop's reference update**, not against the previous hop's stale value — see bug 4 below for why this matters even with instant-snap rise.
- **Seeded with a sensible default at track start / source change, not zero** — prevents both a track that jumps straight into loud material and one that builds up gradually from showing artificially inflated bars while the reference ramps up from nothing.
- Reference decay tau and the seed value are tunable constants per the requirement above. The seed value is `kAgcMinReference` — the same constant that also serves as the AGC reference's decay floor (`agc_reference_[band] = std::max(agc_reference_[band], kAgcMinReference)`, §4's AGC mechanism above). One constant, two roles: it's both "what the reference starts at before any real data exists" and "how low the reference is ever allowed to decay." This was previously undocumented — closes the gap this section used to flag ("not yet captured verbatim").

**pffft's real-FFT output has a specific, ordered packing (DC term, Nyquist term, then interleaved real/imaginary pairs) — get this wrong and magnitude/peak-frequency computation corrupts silently, no crash, no obviously wrong output at a glance.** This is an external-library contract, not a project decision, but it's load-bearing everywhere band energy and peak frequency are computed from the raw FFT output — worth knowing this is where to look first if banding or peak-frequency results ever look subtly wrong (e.g., DC/Nyquist bleeding into a real band) despite the surrounding logic checking out.

*Bugs found and fixed, in order (each confirmed with traced per-hop data, not accepted on plausibility):*
1. **Single global reference collapsed treble variation.** A single fixed constant, calibrated off whichever band naturally hit it (almost certainly bass/low-mid, since that's where music energy concentrates), meant every other band was measured against a scale unrelated to its own typical range — treble bands couldn't show meaningful variation even at their own effective local maximum. Some left/mid skew is real and expected (physics of where energy concentrates); this bug suppressed the top end well beyond that real skew. Static per-band constants were considered as a fix and rejected in favor of adaptive, since the goal is working well across arbitrary audio rather than material tuned to a specific calibration set.
2. **AGC fed from raw energy while the display used smoothed energy — a numerator/denominator mismatch.** The fast-attack/slow-release display envelope rides higher than a plain average (spends more time near recent peaks), so dividing a peak-biased numerator by an unbiased denominator systematically inflated the ratio (explained excess clipping) and caused large relative swings near silence, where both signals collapse toward the same tiny noise floor. Fix: feed the AGC from `smoothed_energy_`, the same quantity being displayed — numerator and denominator became the same signal at two timescales, self-consistent by construction.
3. **A symmetric one-pole reference converges toward the current level rather than providing headroom.** During a sustained loud passage, a plain trailing average settles close to the signal it's normalizing, pinning the ratio near 1 regardless of content (observed as a flat 60–90%+ reading regardless of loudness). Fix: asymmetric rise/decay (peak-hold shape, as in the settled design above) — this is what let normal passages read as a modest fraction (~10–45%, tracking real loudness) instead of pinned near the ceiling.
4. **A blended (tau-based) rise, even after moving to asymmetric rise/decay, was still not fast enough for bursty/gappy content.** The rise branch of a one-pole filter only integrates while the input exceeds the current reference — for peaky, gappy material (a choppy intro), the signal spends very little time actually above the reference at any instant, so the *effective* catch-up rate was far slower than the nominal tau suggested (observed: reference still visibly climbing after 19+ seconds on one track, never settling). This is why classic peak-hold meters use near-instant attack rather than any blended rise, however fast — fixed by switching to true instant-snap (`reference = max(reference, value)`, no tau at all) rather than further tightening a rise tau, which would only have shrunk the gap, not closed it.
5. **A one-hop read/update ordering bug remained even after instant-snap rise.** If a hop's ratio is computed against the *previous* hop's reference, before the reference is updated to reflect the current hop's own energy, a single-hop overshoot spike is structurally guaranteed on the exact transient hop — true regardless of how fast the rise mechanism is, since it's a staleness bug, not a timing-constant bug. Traced peak ratio of 7.78 on one event, worse for bands that had been dormant (larger first climb needed) — this was the actual source of the "smooths out over the course of a song" perception, since it's each band's reference needing a big first catch-up then staying primed, not global system settling. Fixed by ensuring the reference is updated before the ratio is computed within the same hop. Verified after the fix: max ratio exactly 1.000 across every window checked, zero overshoot anywhere — confirmed closed, not just reduced.

*Ruled out, with proof rather than assumption:* after all five fixes, remaining perceived visual "jitter" was checked against the possibility of further data-pipeline instability and ruled out mathematically, not just empirically — a large (>0.3) single-hop swing can only be produced by a genuine attack event, since neither mechanism capable of producing a fast *fall* (reference decay, ~0.03%/hop; envelope release, ~5%/hop) can reach that magnitude in one hop. 100% of large swings in the checked data were rises, confirming the data pipeline is correct and the remaining visible jitter is the throwaway debug bar-chart rendering genuinely fast, legitimate onset-driven data with no frame interpolation (~93Hz feature updates against 60fps display) — a renderer concern, not a data concern, and out of scope for this pass since that rendering code is disposable ahead of the real spectrum visual module (§6) being built against the compositor (§5).

## 5. Layer & Compositor System

**Rendering model:** each active layer renders to its own offscreen texture (framebuffer). The compositor then stacks textures in order — this is what makes arbitrary mixing possible, since layers never fight over one shared canvas. **Every offscreen texture must be cleared to fully transparent (alpha 0), not opaque black, before a visual module draws into it.** An opaque-black background composites incorrectly under every blend mode except normal — additive, multiply, and screen all treat background transparency as meaningful, and an opaque background silently produces wrong output rather than an obvious failure. This is a requirement for every visual module (§6), not something to fix per-module after the fact — found as a real bug during milestone 3 when milestone 2's waveform/spectrum modules (built before the compositor existed to expose the problem) needed correcting.

**raylib's render-target state is not a stack.** Every layer must fully finish rendering to its own offscreen texture — `BeginTextureMode()`/`EndTextureMode()` fully paired and closed — before the compositor's own texture mode (for `output_`) is opened. A nested `BeginTextureMode()` call while `output_`'s texture mode is already active has its matching `EndTextureMode()` reset to the screen framebuffer instead of restoring `output_`, silently breaking the composite target. This is why the render loop's structure is "render every layer to completion first, then composite the already-rendered textures below" rather than any interleaved or nested ordering — found as a real implementation constraint during milestone 3, not a hypothetical.

**Disabled layers (`enabled=false`) are skipped entirely, not rendered-then-hidden.** The compositor doesn't call a disabled layer's `render()` at all — no offscreen texture work, no compositing pass for it. This is cheap by construction, not an optimization to add later.

**Layer data model (conceptual):**

```
Layer {
  visual_type: enum (waveform, spectrum, particles, fractal, flow_field, geometric, ...)
  visual_params: struct          // per-type settings
  opacity: float
  blend_mode: enum (normal, additive, multiply, screen, ...)
  tint_color: optional
  palette_override: optional
  reactivity: LayerReactivity    // see struct below — freq_band, source, sensitivity
  enabled: bool                  // default true; compositor skips render() entirely when false
}
```

**`LayerReactivity` (real struct, `src/visuals/visual_module.h`):**

```
struct LayerReactivity {
    std::optional<std::size_t> freq_band;   // nullopt = Global; else [0, kNumBands)
    ReactivitySource source = ReactivitySource::GlobalBeat;
    float sensitivity = 1.0f;
};
```

**`ReactivitySource`, `VisualType`, and `LayerBlendMode` live in raylib-free headers — `src/visuals/reactivity_source.h` and `src/compositor/layer_types.h` respectively — specifically to stay usable from translation units that also need `windows.h`.** This has now mattered twice, for two different reasons: originally to avoid a `visuals/` ↔ `compositor/` circular include (`Layer` needs these enums, visual modules need `Layer`-adjacent types), and again at milestone 8 when `panel_message.h` needed these same enums in the same translation unit as `ui_host_webview2.cpp`, which pulls in `windows.h` — and `windows.h` collides with raylib's own symbols (`CloseWindow`, `ShowCursor`) if both are visible together (the same class of collision `FileProducer`'s pimpl structure was built to avoid, §3). Keeping these enums dependency-free is what let the second collision be fixed by extraction rather than reintroducing a pimpl wrapper or reordering includes. Don't move these back into a raylib-touching header without resolving both reasons they were extracted.

**`ReactivitySource` has three values: `GlobalBeat`, `BandOnset`, `BandAmplitude`.** A fourth value, `PeakFreq` (reacting to which frequency currently carries the most energy), existed briefly during milestone 6 development and was removed — it never had a defined pulse/visual behavior that made sense for a continuous, non-event value like peak frequency, and no real use case for it was ever identified. Don't reintroduce it without a concrete design for what it should actually drive; the "continuously map peak frequency to hue" idea that came up when discussing it is closer to palette override (§5) than to a reactivity source, and shouldn't be built as a one-off here.

**`sensitivity` (real field: `Layer.sensitivity`, `src/compositor/layer.h`) — per-layer multiplier on top of the shared band envelope (§4).** Clamped to `[kSensitivityMin, kSensitivityMax] = [0.0f, 4.0f]` via `compositor_math::clamp_sensitivity` — tunable constants, not hardcoded literals, tested against real material. Default `1.0f` (identity, matches unscaled prior behavior). Applied differently depending on the reactivity channel:
- **Amplitude channels** (`BandAmplitude`, and any other continuous-value channel): direct multiply on the value, uncapped past 1.0 by design — a layer can genuinely be made more responsive than the raw envelope, not just attenuated.
- **Onset/pulse channels** (`BandOnset`, `GlobalBeat`): multiplies the pulse's snap-up magnitude *before* that pulse's own `[0,1]` clamp — sensitivity affects how easily a pulse reaches full intensity, but never produces an out-of-range value regardless of how high sensitivity is set. Multiplying after the clamp would make sensitivity above 1.0 a no-op, which is why pre-clamp is the correct order.


**Stack position is implicit (vector index), not a separate field.** No `order_index` on `Layer` — position in the stack is just where it sits in the underlying `std::vector<Layer>`, and `move_layer` operates directly on that. This avoids a redundant piece of state that could drift out of sync with actual position, and it's what the compositor already does. Layer identity (a stable reference that survives a reorder — needed for UI selection surviving drag-to-reorder, and for layer preset persistence) is a separate, currently-unsolved concern — see §9.

**Naming note: the actual enum is `LayerBlendMode`, not `BlendMode`.** raylib defines its own global `BlendMode` enum; naming this type identically would collide. Worth remembering if a future rename "for consistency" is tempting — it isn't available.

**Layer stack operations:** add, remove, reorder (drag-to-reorder, same interaction as Photoshop/Premiere layer panels), duplicate. Duplication is a first-class operation — instancing the same visual type multiple times (e.g., three particle layers each mapped to a different frequency band) is an expected, cheap way to build complex visuals without new visual code.

**Layer count cap: 16, a permanent architectural limit enforced in `Compositor` itself** (`kMaxLayers`), not just at the UI/debug-tool level — `add_layer`/`duplicate_layer` return `std::optional<std::size_t>`, `nullopt` at the cap. Chosen for a semantic reason (one per band + global, spec §4), not from measured GPU/performance cost — no profiling of actual offscreen-texture rendering cost at high layer counts has been done. This resolves the "layer count performance ceiling" gap by having *a* documented default cap, not by having verified 16 is the optimal number. Worth revisiting only if 16 is actually hit in practice and feels limiting (duplication makes multiple layers per band a real use case, which the "one per band" framing doesn't fully account for) — raising it later is a one-constant change, not an architectural one.

**Color customization**, two layers of control:
- **Palette override, as built (milestone 7): a shared `Palette` type (`src/visuals/palette.h`), not per-module bespoke color logic.** `struct PaletteStop { float position; Color color; }` — ordered ascending by position (debug-asserted, not release-checked) — held in `struct Palette { std::vector<PaletteStop> stops; }`. Sampling (`palette_math::sample(palette, t)`) linearly interpolates between the two bracketing stops, `t` clamped to the palette's own min/max stop positions. One shared type across all 7 visual modules, chosen over a bespoke-per-module shape specifically to avoid re-solving "how does color vary across this module's content" seven separate times — validated on Spectrum first (the spec's own original motivating example, and the module with the cleanest natural sampling axis) before extending to the rest, rather than building all 7 integrations simultaneously.
- **Post-tint** — a universal, cheaper compositor-stage pass (hue shift / multiply by tint color) applied after rendering, giving "recolor anything" without touching each visual module's internals. Shipped before palette override, per the original sequencing.

**Per-module palette sampling axis — each module samples along whatever its own natural per-element quantity is, confirmed as implemented:**
- **Spectrum/Radial** — band index, normalized `index/(band_count-1)`.
- **Particles/Flow Field** — life fraction, `age_frames/lifetime_frames`.
- **Waveform/Lissajous** — sample/point index along the drawn trace (`palette_math::sample_by_index`, same normalized form as Spectrum's), called once per drawn line segment — not physical position or time directly, but the point-array index, which maps 1:1 to position along the trace for both (left-to-right for Waveform, order along the plotted curve for Lissajous).
- **Fractal** — the shader's existing smooth escape-time value `t` (already computed pre-existing for its rainbow-cycle hue path, not a new quantity) — this is escape depth, not distance-from-set (a separate variable used only for the boundary-alpha fade, untouched by this). Palette is uploaded as a small lookup texture (`sync_palette_texture`, built from `palette_math::to_gradient_pixels`) and sampled in-shader (`texture(paletteTex, vec2(fract(t + hueShift), 0.5)).rgb`) — the one module needing a structurally different integration mechanism than the other six, since its rendering happens per-pixel in GLSL rather than per-element in C++.

**Palette override is a deliberate, understood exception to the tint-blind convention — not a regression of it.** `VisualModule::render()`'s signature now carries a third argument, `const std::optional<Palette>& palette_override`, and each module samples it directly to compute per-element base color before drawing. `tint_color` is unaffected and untouched by this: modules still never see it, and the compositor still applies it exactly once, as a post-render multiply, in the same place it always has. The two are not the same kind of thing and were never in tension: tint is one uniform value applied identically to every pixel of an already-finished layer texture, which is exactly why it could and should stay compositor-side; palette override supplies per-element variation *within* a layer's still-being-drawn content (bar-by-bar, particle-by-particle) — data the compositor structurally cannot reconstruct after the fact, since by the time it sees a layer, that layer is already one flattened texture. Sequence is unchanged: a module draws using palette-sampled colors, then the compositor's post-tint multiply still applies afterward, same ceiling as always (above).

**Tint is a multiply ceiling, not a floor — non-obvious, cost real implementation rework once already.** Because post-tint is applied once, after a visual module's `render()`, as a straight multiply, and a visual module's pre-tint output can never exceed 1.0 per channel, the mathematical result can never be brighter than `tint_color` itself — `pre_tint_value × tint_color ≤ tint_color`, always. There is no pixel a visual module can draw, however bright, that composites out brighter than the layer's own tint. A "brighten on hit" pulse effect must therefore dim toward that ceiling and decay back up to it, not attempt to exceed it (see §6's Spectrum onset-pulse mechanism for the resolved version of exactly this problem). Palette override is the escape hatch this note originally pointed to for a visual module that genuinely needs internal color control beyond what a post-tint multiply can express — now built; don't add a further one-off exception that lets a single visual module peek at `tint_color` directly, since palette override already covers the legitimate need.

## 6. Visual Modules

Starting set, roughly in build order:

1. **Waveform** — raw amplitude over time (simplest, validates the audio pipeline first)
2. **Spectrum/bars** — FFT magnitude per band, classic EQ look
3. **Radial/circular** — spectrum or waveform mapped around a circle
4. **Lissajous** — stereo L/R channels plotted against each other
5. **Particle systems** — spawn/velocity/color driven by a band's amplitude or onset
6. **Plasma/flow fields** — noise fields perturbed by audio
7. **Fractals** — zoom/rotation/color cycling driven by audio
8. **Geometric/abstract** — rotating polygons, tunnels

Each module implements a common interface: given `AudioFeatures` (filtered to its assigned band, if applicable) and its own `visual_params`, render into its offscreen texture. Per §5's rendering model, that texture must be cleared to transparent before drawing — not opaque black — so the compositor's blend modes work correctly regardless of what's stacked above or below.

**Spectrum's `reactivity_source` consumption (resolves a real milestone 4 gap — Spectrum previously ignored `reactivity_source` entirely).** Bar height always tracks the continuous energy/reference ratio (§4's AGC mechanism) regardless of mode — `BandAmplitude` and `BandOnset`/`GlobalBeat` modes show identical height behavior, so a band's current loudness is always visible no matter which reactivity mode is selected. What differs by mode is a per-band RGB brightness pulse layered on top of that same bar, driven independently of height:

- **`BandAmplitude` mode:** no pulse; bar renders at its normal `bar_color` (`WHITE`, the multiply-identity for post-tint) at all times.
- **`BandOnset`/`GlobalBeat` mode:** bar color interpolates between a dimmed rest fraction and full `bar_color`, snapping to full brightness on an onset event and decaying back to the dimmed rest state afterward — same snap-and-decay shape as elsewhere, applied to color instead of height. This resolves the multiply-tint-ceiling constraint (§5): since full `bar_color` is already the brightest a bar can render pre-tint, the pulse dims *below* that and rises back *up to* it, rather than attempting to exceed it.
  - Rest brightness: `kSpectrumOnsetPulseRestBrightnessFraction = 0.55f` (`src/visuals/visual_config.h`), tunable, tested against real material.
  - Decay: `kSpectrumOnsetPulseDecayPerFrame = 0.92f` (`src/visuals/visual_config.h`) — a flat per-frame multiplicative decay, not a time-constant-derived (`tau`-based) coefficient like most other decay mechanisms in this project (§4's envelope, AGC reference). This means its perceived decay speed is implicitly tied to the render loop's frame rate rather than being frame-rate-independent; a minor known inconsistency, not corrected here, worth knowing if the render loop's timing model ever changes.
- Each `SpectrumVisual` instance maintains its own independent per-band pulse state (one decaying value per band + global, `kTotalBands` values) — this is per-visual-module state, not shared audio-pipeline state, and doesn't touch raw flux or violate invariant #2.
- In `GlobalBeat` mode, each bar currently pulses off its own band's individual onset, not a single shared aggregate pulse — the dedicated global pulse slot (index `kGlobalBandIndex`) is computed every frame but not currently drawn. Worth knowing this is the actual behavior if "GlobalBeat" as a name suggests a single synchronized flash across all bars; that's not what it currently does.
- `SpectrumVisual` remains fully tint-blind, per §5's tint/visual-module separation — it has no access to `tint_color`, only to `LayerReactivity` (`freq_band`/`source`/`sensitivity`). This mechanism was deliberately built to hold that separation rather than crossing it, after an earlier design attempt would have required threading `tint_color` into the visual module directly.

**`WaveformVisual`'s onset-pulse stale-band bug: fixed, not just flagged.** Previously a single scalar (`onset_pulse_`) that didn't reset when a layer's `freq_band` changed at runtime, briefly showing a stale decaying pulse carried over from the previously-selected band. Fixed by adding a `last_freq_band_` member, compared against the current `reactivity.freq_band` each frame in `render()`, resetting `onset_pulse_ = 0.0f` on mismatch before the existing decay/target logic runs. `resolve_reactivity()` itself is unchanged (pure, stateless, its existing unit tests still pass untouched) — the fix is additive state inside `WaveformVisual` alone, isolated from every other module. Fixed as part of building Lissajous (below), which shares the same full-signal (not per-band) category and would otherwise have inherited the identical bug fresh.

**Lissajous, as built (milestone 6): true stereo separation, verified end-to-end, not assumed.** `AudioFeatures` gained `waveform_l`/`waveform_r` (each `kWaveformSnapshotSize` floats, same size/shape as the existing mono `waveform`) — this closes the "zero cost later" promise made when canonicalizing to stereo at milestone 5 (above). Real separation, not two copies of the mono mixdown: in `FeatureWorker::drain_ring_buffer()`, `mixdown_to_mono()` and `deinterleave_stereo()` both read `interleaved_scratch_` (the raw canonical-format PCM straight off the ring buffer) independently — neither is downstream of the other. `waveform_l`/`waveform_r` are copied into the triple-buffer snapshot the same way `waveform` is; publish cost is unaffected (the triple-buffer swap is an atomic index exchange, not a memcpy — the two new arrays only add static struct footprint, roughly +24KB total across the three snapshot buffers, negligible).

**Reactivity: modulation-only, same category as Waveform, not per-band like Spectrum/Radial.** Lissajous displays a single continuous stereo trace, not per-band bars — there's no natural "per-band slice" of an X/Y figure, so `freq_range`/`reactivity_source` scoping follows Waveform's existing pattern (amplitude modulates continuously; onset triggers the shared decaying-pulse mechanism) rather than Spectrum's per-band branching. Pulse state is an independent per-instance member from the start (same as every visual module — each layer owns its own instance via `clone()`), not shared across layers or duplicates.

**The rendering is a direct X/Y plot of raw `waveform_l`/`waveform_r` samples — no trailing-window subset, no per-point fade.** Every sample in the full snapshot (1024) is plotted every frame, connected by line segments of uniform color/thickness; oldest and newest samples look identical. This means the displayed shape's size tracks raw instantaneous amplitude directly and continuously — a genuine sustained, high-amplitude passage holds a large open shape for as long as the sustain lasts; a decaying transient (most real music, most of the time) causes the shape to visibly pulse open and collapse back toward the origin as amplitude falls, since neither channel's raw samples pass through any envelope smoothing or AGC processing (that machinery only applies to `band_energy`, a separate FFT-derived quantity — raw waveform display, for both Waveform and Lissajous, has never been smoothed). This is not a bug: on mono or heavily-centered content, the trace correctly collapses toward a diagonal line (`x == y` when both channels are identical); on real stereo content, it opens into whatever pattern the two channels' actual relationship produces — the technique only shows the clean geometric curves associated with the name "Lissajous" when fed simple periodic tones, not complex real music, which is expected, not a defect.

**Nonlinear amplitude scaling added to reduce how dramatically the shape swings between fully open and collapsed.** Raw samples are passed through a compressive curve before being scaled to canvas coordinates — quiet samples are boosted proportionally more than loud ones, so quieter passages hold more visible shape without loud passages clipping or distorting. Curve strength is a tunable constant (not hardcoded inline), specifically so it can be exposed as a real user-facing control once milestone 8's UI exists — this is a display-time transform inside `LissajousVisual` only; `waveform_l`/`waveform_r` on `AudioFeatures` itself remain raw, unscaled samples, and no other visual module is affected.

**A trail/persistence mechanism (keeping several recent frames' worth of points visible with fading opacity, rather than fully redrawing only the current window each frame) was discussed as a further option to make the display read as a more continuous, layered figure rather than one shape pulsing in isolation — not yet built.** Worth building only if the nonlinear scaling above turns out to be insufficient on its own; would be a real, separately-scoped feature (its own fade-rate tunable, its own persistence-buffer design) rather than a small addition.

**Radial/circular, as built (milestone 6): spectrum-style, not waveform-style.** Chosen over a waveform-bent-into-a-ring alternative and over a dual-mode toggle — reuses `SpectrumVisual`'s per-band reactivity/pulse logic directly, just mapped to angular position around a circle (band index → angle slot) instead of horizontal position. Inherits Spectrum's `reactivity_source` branching, onset-pulse mechanism, and idle handling as-is; no separate reactivity design needed for this module.

**Bar height is fully derived from the gap between `inner_radius_fraction` and `max_radius_fraction` — not an independent value.** This was a real design correction, not the original implementation: bar height started as an independent fixed value, which meant an inner radius set high enough (approaching outer radius) made bars shrink to nothing or, in the other direction, could imply bars reaching past the canvas edge — two unrelated parameters producing broken-looking combinations at their extremes. Fix: 0% amplitude renders at exactly `inner_radius_fraction`, 100% amplitude renders at exactly `max_radius_fraction`, with everything between scaling linearly across that gap. This collapses what were three semi-independent controls (inner radius, outer radius, bar height) into two — inner and outer radius alone now fully determine both the empty-center size and the maximum bar reach, which is a deliberate simplification, not a lost capability: the previously-independent height field added no expressiveness the two radii didn't already imply once properly linked (outer-max + inner-min gives maximum stretch; outer-max + inner-max gives short, dot-like bars).

**Guardrail: `inner_radius_fraction` must never reach or exceed `max_radius_fraction`.** A minimum enforced gap constant (tunable) prevents the two values from being set into a combination that collapses or inverts the available range. Enforced by clamping/rejecting invalid configurations, not left to the caller to avoid.

**Particles, as built (milestone 6):**
- **Emission model:** `BandOnset`/`GlobalBeat` spawn a decaying-magnitude burst of particles on each onset event (same shape as Spectrum's color pulse, different consequence — particle count instead of brightness). `BandAmplitude` spawns continuously, at a rate proportional to the band's energy/AGC-reference ratio — no burst. This mirrors Spectrum's existing height-vs-pulse split (a continuous channel always active, a discrete channel only on onset events) applied to spawn behavior instead of color.
- **Motion:** particles spawn from a point offset from center by a per-layer `inner_radius_fraction`-equivalent, along that band's angle slot (same per-band angle grid as Radial, so a band-scoped Particle layer visually lines up with a band-scoped Radial layer at the same index) — global-scoped layers spawn at a random angle. Velocity direction is fixed at spawn (grid angle ± jitter) and magnitude scales with amplitude/sensitivity at spawn time; neither is recalculated after spawn.
- **Pool:** fixed preallocated `std::array<Particle, kMaxParticles>` (`kMaxParticles = 1024`, tunable) — no per-frame heap allocation, consistent with `AudioFeatures`'s and the ring buffer's existing no-per-frame-allocation precedent. Color is a single tint-blind `particle_color` param (compositor applies tint after, same as every other visual) — per-particle color variation (e.g. by spawn band or velocity) was considered and explicitly rejected as crossing into palette-override territory (above), which is deliberately deferred; no visual module does per-element color variation today.
- **Timing convention:** motion and lifetime are frame-scoped (px/frame, frame-count lifetime), not `GetFrameTime()`-based real-time. This matches the existing convention across every visual module (`kSpectrumOnsetPulseDecayPerFrame` and friends are all flat per-render-call multipliers) rather than introducing a second, real-time-based timing model alongside the frame-scoped one already used everywhere else in `visuals/`. The frame-scoped-vs-real-time inconsistency itself is a known, accepted tradeoff (§9) — not something to fix per-module as new modules are added.

**Bug found and fixed: `BandAmplitude` mode had no idle gate, producing a continuous low-level particle trickle even during genuine near-silence.** `smoothed_energy_` decays asymptotically and never reaches a true zero (§4), so a spawn-rate formula reading it directly always produces some small nonzero rate — unlike `SpectrumVisual`, where the same "small value ≠ zero" property just makes a bar look small (bounded by `kMinBarHeightPx`), for Particles it meant literally continuous spawning with no "off" state, which read as excessive/clogged streaming during quiet music and never fully stopped during genuine silence. Fixed with the same `band_idle` gate `WaveformVisual` already used correctly (`if (idle) rate = 0.0f;` before the rate is used) — a plain zero-out is sufficient here since this is a pure product with no additive floor term (unlike the onset threshold's `max(adaptive, absolute_floor)` shape elsewhere in the codebase). Secondary hardening added in the same pass: `ratio` is now clamped to `[0,1]` before use (matching `SpectrumVisual`'s existing `std::clamp`), as insurance against an AGC overshoot edge case that spec §4 documents as verified not to occur under normal operation, but wasn't previously guarded against here the way Spectrum guards it.

**Off-canvas cleanup: particles are recycled immediately on leaving the canvas, not left to expire by lifetime alone.** Before this fix, only age-vs-lifetime was checked, so a particle that had already flown off-screen kept occupying a pool slot and being stepped/drawn (invisibly) until its full lifetime elapsed — wasted pool capacity that gets worse the more distance/lifetime tuning pushes particles further off-screen. Fixed by adding a bounds check in `step_pool` alongside the existing age check. The bounds check uses a margin equal to the particle's own drawn radius, not a bare position-vs-canvas-edge comparison — checking bare position would recycle a particle the instant its center crosses the edge while its drawn circle is still partially visible, producing a visible pop/clip at the boundary instead of a clean disappearance past the edge. No wraparound/toroidal behavior exists or is planned for this visual (a radial burst fading outward has no case where "gone off-screen" carries meaning worth preserving), so immediate recycle on exit is the correct behavior, not a simplification of something richer.

**`GlobalBeat` mode firing behavior on particles is accurate detection, not over/under-triggering — a known, accepted limitation on sparse/quiet material.** Firing on every real transient during a full mix (including an extra hit on an off-beat, e.g. a snare ghost note) is correct onset detection working as designed, not spurious extra triggering. Inconsistent firing during genuinely sparse, quiet, high-frequency-transient passages (e.g. a solo hi-hat pattern) is the same class of limitation already documented for the ride-cymbal case that drove the onset-floor/AGC investigation (§4) — quiet, sparse, high-frequency content sits closest to the adaptive threshold's noise margin regardless of how much floor/AGC tuning has been done. Not treated as a bug to chase further; `BandAmplitude` mode exists specifically for cases wanting continuous rather than discrete reactivity.

**Flow Fields, as built (milestone 6): reuses `ParticlesVisual`'s pool/lifetime/cleanup infrastructure as-is; velocity-update and spawn-position are both new.**

- **Noise generation: hand-rolled value noise, not a new dependency.** Checked first whether an existing library covered this (raylib's `GenImagePerlinNoise` is whole-image, not per-point callable; nothing in miniaudio/pffft applies) — implemented as hashed-corner value noise instead: an integer hash at each lattice corner (`flow_field_math::hash2d`), bilinearly interpolated with a smoothstep fade (`flow_field_math::value_noise2d`, range `[-1, 1]`). Direction lookup (`flow_field_math::field_direction`) maps noise output to an angle, then to a unit vector, parameterized by a turbulence frequency and a time-phase (the field's animation driver).
- **Velocity: steered toward the local field direction each frame, not fixed at spawn.** This is the fundamental change from `ParticlesVisual` — `flow_field_math::steer_velocity` blends a particle's current velocity toward the field's direction at its current position, at a rate controlled by `kFlowFieldSteerFactor` (a full steer factor snaps directly to the target direction; zero keeps the particle's current heading unchanged).
- **Spawn position: uniform random across the canvas, not radial-from-center.** `ParticlesVisual`'s existing band-angle-from-center spawn scheme (`spawn_direction`/`spawn_position`) was initially reused, then replaced this same session once it became clear it didn't fit — flow fields are meant to fill the whole canvas with organic motion, and clustering every tracer's origin at one central point actively worked against that. Fixed with `flow_field_math::random_canvas_position` (independent uniform distribution over the full width/height). `freq_band` scoping is confirmed reactivity-only after this fix — it selects which band's amplitude/onset drives turbulence, evolution, ripple, and burst, but never affects spawn position.
- **Turbulence and evolution speed are both live, amplitude-driven scalars, not fixed constants.** Computed each frame as `base * (1 + amplitude_ratio * sensitivity)` — turbulence affects the noise field's spatial frequency (how chaotic/complex the directions look), evolution affects how fast the field's time-phase advances (how quickly the whole pattern churns). Independent of each other; both can be active simultaneously, per the original design decision that these aren't mutually exclusive.
- **Onset-driven ripple: an expanding shockwave ring, not a noise-field distortion or a single instantaneous kick.** Neither of the two mechanisms originally considered (perturbing the noise input directly, or a fixed directional impulse) — a `Ripple{origin, age_frames, active}` slot (fixed pool of `kMaxFlowFieldRipples`) activates at canvas center on an onset event; each frame its radius grows (`age_frames * kFlowFieldRippleSpeedPxPerFrame`). Every active particle receives a radially-outward push (`flow_field_math::ripple_impulse`) added on top of its steered velocity, with magnitude peaking exactly where the ring currently is (a triangular falloff across `kFlowFieldRippleBandwidthPx`, via `ripple_influence`) and zero elsewhere — a traveling disturbance that displaces particles as it passes through them, rather than a static or instantaneous effect.
- **Onset-driven burst spawn reuses `ParticlesVisual`'s existing burst mechanism unchanged** (`spawn_into_pool`, `accumulate_spawn_count`, `faded_color`, etc., called as-is) — a separate mechanism from the ripple, and both can fire on the same onset event since they affect different state (particle count vs. existing particles' velocity).
- **Default tuning differs from `ParticlesVisual`'s** (longer lifetime, lower spawn rate, smaller burst count) to suit a flowing-stream look rather than Particles' burst-heavy character — all values in `visual_config.h`, flagged untuned starting points per project convention.
- **Debug-tool exposure deliberately narrow, per the "full parameter set built, most left compile-time-only" design decision:** only `h` (toggle ripple-on-onset) and `j` (toggle burst-on-onset) are wired, both no-ops on a non-FlowField-selected layer. Turbulence, evolution, grid resolution, and every ripple/burst tuning constant are compile-time only — fine-tuning is deferred to milestone 8's real UI, consistent with how Particles' and Lissajous's own tunables were already treated the same way.

**Fractals, as built (milestone 6): three approaches were prototyped on separate branches and evaluated before deciding which to keep, since fractal generation covers a genuinely wide range of technique/cost/visual-character tradeoffs (recursive geometric shapes, IFS/flame-style point accumulation, GPU-shader escape-time rendering) with no obvious single right answer.**

**Recursive geometric — kept, currently limited to one shape.** Bounded-recursion geometric fractal (a fractal tree), drawn with plain raylib draw calls, no new subsystem — audio-driven branch angle/length and recursion depth, same conventions as every other module. Working correctly, but visually limited: only one seed shape currently exists. Adding a small set of alternate shapes (e.g. Sierpinski triangle/carpet, a radiating star pattern), selectable per layer, is a real, wanted follow-up — not yet built. A related idea (exposing spawn point and/or generating multiple shape instances from one base calculation) was also raised and deliberately parked for after milestone 8's UI exists, same treatment as other recently-deferred per-module parameters (Particles, Flow Fields, Lissajous).

**IFS/flame fractal — attempted, real bugs found and fixed in sequence, ultimately abandoned.** Chaos-game point accumulation into a density buffer, color-mapped by density. Went through several genuine, confirmed bugs: an initial concern about the base transform coefficients was raised, numerically simulated, and found to actually be correct (the transforms do properly tile the canvas — an early "fix" attempt was caught and reverted before being applied, since simulating it showed it would have made coverage worse, not better); the real bottleneck was decay/accumulation timing (points faded far faster than the ~1.7% of cells touched per frame could build into a visible cloud); a subsequent fix revealed a splat/filtering gap (single-cell hits with nearest-neighbor texture upscaling produced hard-edged isolated squares rather than a soft cloud, explaining why partial fixes still looked like scattered points rather than flame-like density); log-density color scaling was tried and made no visible difference, indicating the real limiting factor was insuf­ficient sustained point accumulation before decay, not color mapping. This is a genuine, hard tradeoff between visual reactivity (fast decay, feels alive) and recognizable fractal structure (needs sustained accumulation, which fast decay prevents) — resolving it properly would need either a much larger per-frame point budget or a dual-buffer design (a slow, persistent structure buffer plus a fast, reactive highlight layer). **Abandoned, not merged, after a controlled performance check:** stress-testing every other shipped module (including Recursive Geometric) at 32 layers, including randomized batch-generated configurations (`-n 32`), showed no slowdown — isolating Flame specifically as unusually expensive per-instance (its per-layer density buffer, CPU-side decay pass, and texture upload have no equivalent cost in any other module). Given the unresolved reactivity/structure tradeoff and the confirmed, isolated performance cost, continuing was judged not worth it relative to five other working modules. The branch and its history remain available if this is ever revisited.

**GPU shader-based Mandelbrot/Julia — kept, the first custom shader in this codebase.** Real-time escape-time rendering (`z = z² + c`) computed per-pixel in a GLSL fragment shader, since a full-canvas per-pixel iteration is far too slow to compute on the CPU at 60fps. raylib's `LoadShader` loads the shader; a full-canvas rectangle is drawn through it via `BeginShaderMode`/`EndShaderMode`; audio-derived values are passed in as uniforms via `SetShaderValue`. This is genuinely new infrastructure for the render pipeline — no other visual module uses a custom shader — but confirmed to still respect the existing compositor contract: the shader is tint-blind (never receives or reads `tint_color`, same as every other module — the compositor's post-tint multiply pass happens afterward, on the already-rendered texture, unaware this module's rendering happened via shader rather than normal draw calls) and clears to transparent per invariant #4.

- **Reactivity design: audio drives evolution *rate*, not value, directly — reusing Flow Fields' established pattern.** The Julia orbit's angular speed scales with smoothed amplitude the same way Flow Fields' turbulence/evolution scalars do (`base * (1 + amplitude_ratio * sensitivity)`, accumulated into a persistent phase every frame) — audio speeds up or slows down an always-running motion, never sets a value directly or snaps. Zoom is a separate, deliberately audio-*independent* ambient "breathing" oscillation (a fixed-rate sinusoid) — the two were explicitly decoupled after recognizing that tying both to the same amplitude signal would make them always speed up and slow down in lockstep, reintroducing a flashy/chaotic feel through *correlated rate* even with each channel individually smoothed. Decoupling (rather than giving each channel a different filter of the same signal) was chosen since it's a structural guarantee, not just a reduced-probability mitigation — nothing in real audio can make a fixed, non-audio-driven oscillation suddenly synchronize with an audio-driven one.
- **Real bug found and fixed: the zoom-breathing range introduced values below what had ever been exercised before, causing periodic near-invisible frames.** Zoom had previously only ever ranged upward from a baseline of 1.0; adding a symmetric breathing oscillation introduced zoom values below 1.0 for the first time, and certain camera/zoom combinations in that new range landed on genuinely near-featureless regions of the fractal (a real, expected property of Julia sets — some regions are visually "empty" at certain zoom levels). Fixed by keeping the breathing motion's floor at the previously-validated 1.0 minimum, rather than allowing it to swing below a range no prior work had confirmed showed real structure.
- **Real bug found and fixed, predating this session's redesign: the orbit's fixed radius mostly swept disconnected ("dust") regions of Julia parameter space.** Confirmed by direct numerical escape-time sampling around the actual orbit circle (not simulation-by-analogy) — only ~12.5% of the orbit (a few narrow arcs) produced a connected, visually structured Julia set; the remaining ~87.5% escaped almost immediately, rendering as empty. This explained every reported symptom precisely: starting blank (orbit phase begins outside a good arc), briefly appearing as the orbit sweeps through a good arc, going blank again, and multiple layers' aggregate flicker extending in duration without ever resolving (each layer's phase starts independently, at a different point relative to the good arcs). This bug existed in the original fixed-radius orbit design from before this session's other changes — it simply hadn't been isolated as a distinct cause until the zoom/tint issues around it were cleared away. Fixed by finding an orbit radius/path with substantially better connected-region coverage, using the same direct numerical measurement technique that found the problem.
- **Color: static or slow time-based cycling only — no audio-reactive hue.** Onset-driven hue flashing (reusing the same snap-and-decay accent convention as every other module's onset pulse) was tried and found to feel wrong specifically at full-canvas scale — an accent that reads as a satisfying punch on a small bar or line reads as a jarring, disorienting flash when applied to something that fills the whole frame. Removed rather than damped; hue is not tied to `band_onset` or any other audio-reactive input.
- **Color/opacity constrained to the fractal's actual visible structure, not applied uniformly across the full canvas.** Full color/opacity across every shader-touched pixel (regardless of whether that pixel was part of the fractal's structure or empty space) made any color effect cover the entire screen, and — independent of the hue-flashing fix — is also what full-canvas-tint complaints about the shader were actually about. Pixels within the set plus a boundary margin (tunable, roughly 15-20px in current tuning) render with real color/opacity; pixels well outside that margin render fully transparent, letting layers beneath show through, consistent with every other module's transparent-background requirement.
- **Orbit rotation center and direction exposed as per-layer parameters** (`julia_orbit_center_x/y`, default origin; `julia_orbit_clockwise`, default true) — a plain sign flip for direction, no other orbit math touched. **These are in Julia-constant parameter space, not screen space** — they change which region of Julia-constant-space the orbit sweeps (altering the fractal's shape/character as it animates), not where on the visible canvas the animation appears. A screen-space version (panning where on the canvas the motion is visually centered) was considered and explicitly deferred — it would require adding a genuine camera/pan transform to the shader's pixel-to-math-space mapping (which currently has no such concept, always centered at screen-center) and re-validating that the zoom-breathing and boundary-margin logic both still behave correctly relative to a non-fixed visual center. Comparable in scope to the shader work already done this session — worth doing deliberately later, not as a quick follow-on to what was just stabilized.

## 7. UI Architecture

**Terminology note:** this section covers two distinct concepts that both got called "preset" loosely elsewhere in discussion — keep them separate. A **layer preset** is a saved layer-stack configuration (which visual layers, their params, order) that the user creates and recalls, potentially many of them. A **theme** is one of a small, fixed set of built-in UI skins (Y2K, Frutiger Aero, etc.) selectable from the control panel — not user-created, not open-ended. They're unrelated data: don't conflate their storage, their UI controls, or their persistence format.

**Two separate native windows**, not one process trying to share a GPU compositing tree:

1. **Control panel window** — WebView2-hosted HTML/CSS/JS. Owns the layer stack management UI: add/remove/duplicate/reorder layers, per-layer opacity/blend mode/tint/freq mapping, layer preset save/load, and theme selection. WebView2 was chosen over hand-rolling widgets in raylib specifically to hit real Y2K/Frutiger-Aero visual fidelity (gradients, glass/blur, chrome) — see rejected alternatives below.
2. **Visualizer window** — raylib, renders the composited layer stack. Supports a fullscreen mode with minimal chrome: a small, subtle on-screen button to exit fullscreen, in addition to a hotkey.

**No shared-surface compositing.** The two windows don't attempt to render through each other (e.g., control panel glass showing the live visualizer behind it) — each renders against its own background. This avoids needing WebView2's Composition Hosting API / DirectComposition interop with raylib's OpenGL context, which would otherwise be required to have one surface show through the other.

**Fullscreen behavior:**
- Entering fullscreen is triggered either by a hotkey or a clickable button in the control panel UI.
- On entering fullscreen, the control panel window closes/hides rather than staying open-but-covered.
- Exiting fullscreen is available via the same hotkey or the subtle on-screen button in the visualizer window itself.

**Theming:** a fixed set of built-in themes (data-driven — palette, gradients, chrome/glass treatment per theme), selectable from the control panel, not an open-ended user skin/modding system. Closer to "pick a WinAmp skin from a list" than "build your own skin." Not to be confused with layer presets (above) — themes affect only the panel's own appearance, not the layer stack.

**Packaging and distribution: a self-contained portable folder, no install step.** This app is a portfolio/demo piece shared casually with people, not installed software with an ongoing footprint expectation — a folder someone can delete to "uninstall" fits that better than a formal installer with registry entries. Concretely:
- **WebView2: Fixed Version, bundled as a folder next to the `.exe`**, referenced at startup via `browserExecutableFolder` (not system-installed, no registry entries, no admin rights needed). This is a deliberate departure from Microsoft's general recommendation (Evergreen is their default advice for most apps) — chosen specifically because it enables true no-install distribution, which Evergreen doesn't support the same way. Real cost: the Fixed Version payload is large (roughly 250–350MB depending on architecture as of current WebView2 releases), accepted as a normal size for this kind of casual download/share, not something to optimize away.
- **CRT: static linking (`/MT`)** — no VC++ Redistributable dependency, consistent with the same no-install-step goal. Since Fixed Version WebView2 already means no installer is needed for that dependency, dynamic linking's usual justification (smaller binary, paired with an installer that also handles the redistributable) doesn't apply here.
- **Layer presets live in a `presets/` folder relative to the application** — not an OS-provided application-data location, since a portable app has no installed path to rely on. Ship with a couple of demo presets included by default. Exact file format/schema still to be defined when layer preset persistence (§9) is actually built.

**Platform-facing interfaces, both designed swappable even though only Windows is implemented:**
- Audio: the existing `push_frames` producer interface (§3) — implementations are per-OS (WASAPI now; Core Audio/PipeWire documented, not built).
- UI: a `UIHost` interface abstracting the platform webview embed. WebView2 implements it now; a future Linux/macOS implementation (WebKitGTK, WKWebView) would satisfy the same interface without changing the state-bridge protocol or app-side logic. This is what keeps "Windows-first, cross-platform later" a swap rather than a rewrite — see `CLAUDE.md` for the do-not-violate version of this rule.

**State bridge:** layer stack state, live theme selection, and any UI-visible audio-derived data (if the panel shows anything live-reactive) are marshaled across the C++/JS boundary via message-passing (`postMessage`/`ExecuteScript`), using the same JSON shape as layer preset persistence (§9) where applicable, rather than inventing a second serialization format. Theme selection itself doesn't need this — it's a simple identifier, not a schema of its own.

**Native→panel protocol, as built (milestone 8): 3 message kinds, pushed on action, not every frame.** `layer_stack`, `preset_list`, and `status` are pushed to the panel after each applied action (an add/remove/reorder/field change/preset load), not on a per-frame timer — matching the message volume the dispatch queue design already assumed (human-interaction speed, not audio-rate). The JS side does keyed DOM diffing on receipt — list items are reused by `layer_id` rather than the DOM being rebuilt wholesale, and whatever control currently has input focus is skipped during a diff. This isn't a performance optimization, it's a correctness requirement: without skipping the focused element, a state push arriving mid-interaction (e.g., while dragging a slider) would visually yank the control out from under the user's own input.

**Generic per-layer panel controls, as built:** opacity, blend mode, `freq_band`, `reactivity_source`, `sensitivity`, `enabled`, plus layer management (add/remove/duplicate/drag-to-reorder) and preset save/load. `freq_band` and `reactivity_source` are independent dropdowns with no auto-coupling between them — this matches the underlying data model, which has no such invariant (the debug tool's bracket-key convenience for cycling a valid pair together was a debug-tool-only behavior, not a data-model rule). **Visual type is not editable on an existing layer** — chosen once at add-time only, since changing it would discard that layer's module-specific params; this is a real, deliberate scope boundary, not an oversight. **Tint is not exposed as a manual panel control** — layers still get their color via the existing index-based HSV-wheel assignment (`layer_palette_color`/`reassign_tints`, §5), reassigned automatically on any stack-changing operation, same as the debug tool.

**Bug found and fixed: panel-added layers didn't get an assigned tint, staying default white.** The original decision not to auto-assign tint for panel-added layers was a reasonable-looking scope call at the time (tint wasn't in the explicit generic-fields list) but produced a real visible defect once used — confirms the value of flagging design calls rather than deciding them silently, since this was caught and fixed rather than shipped. Fixed by extracting `layer_palette_color`/`reassign_tints` out of `app.cpp` into shared `compositor_math`, so both the debug tool and the panel's message-handling path (`panel_message_apply`) call the same logic rather than duplicating it.

**Panel's remove-layer path only reassigns tints when a layer was actually found and removed — a deliberate deviation from the debug tool's unconditional reassignment.** The debug tool always reassigns tints on any `X` press, even a no-op (nothing at that index). The panel path checks first, since an unconditional reassignment on a no-op remove would overwrite every other layer's tint for no reason if a stale/duplicate remove message were ever processed — a more defensive posture than the debug tool needs, appropriate given the panel is a new, less-controlled input surface than a single local keyboard.

**Fullscreen has no panel button** — the existing hotkey (F11) covers it; a button was explicitly left as optional scope and not built.

**New security surface: `preset_file_io::is_safe_preset_filename`.** The debug tool only ever wrote a single fixed filename, so path traversal was never reachable through it. The panel is the first place a user-typed filename reaches the filesystem, making this a genuinely new trust boundary, not a pre-existing gap — validated against path traversal, path separators, unexpected extensions, and control characters, tested adversarially per `TESTING.md`'s Security / adversarial input section. **Preset overwrite on save is silent, no confirmation dialog** — matches `preset_file_io::write_file`'s existing, already-tested semantics; not a new decision.

**`UIHost` dispatch model: queue-and-drain onto the render thread, not direct cross-thread calls into `Compositor`.** WebView2 callbacks (state-bridge messages from JS) do not call `Compositor` methods directly — they push a message onto a queue, which the render thread drains once per frame and applies to `Compositor` itself, on the thread that already exclusively owns it. `Compositor` requires no thread-safety changes of its own; the queue is the only new synchronized structure. This reuses the same shape as how the render thread already consumes the `AudioFeatures` triple-buffer snapshot (§4), rather than introducing a second, different concurrency strategy for a second thread boundary. A direct-call/mutex-everything alternative was considered and rejected: it would require every current and future `Compositor` entry point to individually guarantee thread-safety, which is exactly the piecemeal-protection pattern that caused both prior audio-side threading bugs (the ring buffer race, the triple-buffer race — §4) — those bugs came from methods that looked locally correct and weren't, and there's no reason `Compositor`'s methods would be any less prone to that than the audio side's were. A polling alternative (no queue, a single flag checked once per frame) was also considered and rejected as unnecessary complexity for no real benefit over a queue, and less able to preserve exact ordering of multiple rapid UI actions arriving between frames.

**This design's "probably fine, no per-frame processing cap needed" assumption depends on the current 32-layer cap (`CLAUDE.md` invariant #4) and is not guaranteed to hold if that cap is ever raised significantly.** Per-frame message volume is currently bounded by human interaction speed and by how many individual layer-mutation messages could exist in flight at once, which the layer cap limits. If the cap is raised meaningfully in the future (well beyond 32), re-derive this assumption rather than assuming it still holds — don't add a per-frame processing cap to the queue speculatively now, since there's no evidence one is needed at the current cap.

**Rejected alternative:** building all UI (including glass/chrome effects) as custom raylib widgets. Keeps the single-language principle intact but was rejected because hand-rolled shader-based chrome/glass rendering would fall well short of genuine Y2K/Aero fidelity without a large, dedicated engineering investment — the explicit goal here is not looking like a compromised approximation of the aesthetic.

**Security defaults (required behavior, not just a test criterion):** the control panel must ship with restricted navigation (no external URL loading), a Content Security Policy scoping resource loading to local app content, DevTools/remote debugging disabled in release builds, and local file access scoped to the app's own asset/data directories. These are implementation requirements for milestone 8, not optional hardening to add later — see `TESTING.md`'s Security / adversarial input section for how they're verified.

**Theme switching behavior:** selecting a new theme in the panel does not interrupt audio playback — audio continues uninterrupted throughout. The panel's own CSS/theme swap is near-instant and doesn't need special handling. The raylib window, however, pauses rendering while it loads the new theme's chrome assets (border/frame treatment, overlay styling — see the UI handoff docs for what counts as theme-dependent chrome), then resumes rendering once loaded. This is a deliberate, visible pause — chosen for simplicity over a hot-swap approach, since asset loading here is expected to be fast and infrequent (a user action, not a per-frame concern). If this pause ends up feeling wrong in practice, the natural upgrade path is a hot-swap using the same triple-buffering packed-word/CAS handoff pattern as `AudioFeatures` (§4, `CLAUDE.md` invariant #1) — not the simpler 2-slot double-buffer or blind-exchange triple-buffer originally considered here, both of which turned out to have genuine data races and were replaced: load new assets in the background, claim ownership of the shared slot via the same compare-exchange retry loop once ready, no pause at all. Not building that now — noted here so it doesn't need to be rediscovered later.

## 8. Milestones

Each numbered step below is a milestone — a checkpoint with its own completion bar, not just a sequence of work items. See `TESTING.md`'s "Milestone completion checklist" for what to verify at each one; the specific checks that apply depend on what that milestone actually touches (a milestone that adds no new threading code doesn't need a fresh TSan pass, one that adds no visuals doesn't need a human visual review, etc.).

1. **Local playback + feature extraction.** Local file playback working, feature extraction (banding, onset, envelope) computed and validated against synthetic fixtures. This is also where the audio → worker → render thread handoff is first built — concurrency checks apply here from the start, not just later.
2. **First visuals.** Waveform + spectrum bar visuals rendering from live `AudioFeatures`. Proves the render path end to end.
3. **Compositor.** Layer stacking, ordering, opacity, blend modes — built even with just the two visual types from milestone 2, since retrofitting compositing later is harder than designing it in now.
4. **Layer duplication + frequency mapping.** Duplicate operation, per-layer `freq_range`, and `reactivity_source` (global vs. band) all working together.
5. **Loopback capture.** Second audio producer feeding the same pipeline (WASAPI, per the Windows target in `CLAUDE.md`), via a canonical pipeline format (48kHz/stereo/f32, §3) so the ring buffer and `FeatureWorker` are constructed once and never rebuilt on a source switch. Mid-session switching is handled by `ProducerHost` (`src/audio/producer_host.h`), the sole owner of producer lifecycle — `switch_to()` is the only path that can change the active producer, structurally guaranteeing the outgoing producer's `stop()` completes before the incoming producer's `start()` begins (verified against the pinned miniaudio source's actual WASAPI synchronous-join behavior, not assumed; see §3's caveats on that guarantee's version-pinned nature). This is the milestone's actual concurrency-relevant case per the ordering requirement above, verified via automated ordering tests (`producer_host_test.cpp`) plus real rapid-toggle stress testing (100+ switches, varied timing, several minutes) rather than TSan, since WASAPI doesn't exist under WSL2 and the diagnostic build is structurally blind to this interaction.
6. **Remaining visual modules.** Radial/circular, Lissajous, particles, fractals, flow fields, geometric — additive once the architecture above is proven.
7. **Tint and palette.** Post-tint color pass shipped first, then palette override (§5) built and validated on Spectrum before extending to all 7 visual modules.
8. **Control panel UI.** WebView2 window, `UIHost` interface, state bridge, layer stack controls wired to real layer state, and layer preset save/load. Theme selection applied last, once the panel functions — including the pause/resume behavior on the raylib side described above, not just the panel-side CSS swap.

### Gap details


- **Layer preset persistence** — no mechanism yet to save/reload a layer stack (types, params, blend modes, freq mappings) to disk. Without this, every session starts from scratch. Straightforward fix: JSON serialization of the `Layer` struct list. Note: §7's state bridge is specified to reuse this same JSON shape, so the schema needs to be defined once and shared, not designed twice — resolve this gap before or alongside building the state bridge (milestone 8), not independently. This is distinct from theme selection (§7) — a layer preset is a saved layer-stack configuration; a theme is a built-in UI skin. Don't conflate the two when designing the storage format. **Storage location: a `presets/` folder relative to the application** (consistent with the portable, no-install packaging decision below — there's no installed-application-data location to rely on). Ship with a couple of demo presets included, so the app doesn't start completely empty of examples. Exact schema/file format still to be worked out when this is actually built.
- **Layer identity (`layer_id`)** — `Layer` has no stable identity field; the only current reference to a layer is its transient vector position (§5), which doesn't survive a reorder. Purely additive when it's added — a lookup key alongside the existing vector, not a restructuring of it. Not needed yet because nothing currently requires a reference to outlive a single in-memory session, but becomes necessary once the control panel needs UI selection to survive a drag-to-reorder, and once layer presets need to reference a specific layer across a save/load round-trip.
- **Output/export** — not yet decided whether this stays a live on-screen visualizer only, or needs a "render to video file" path. Affects whether rendering must be decoupled from real-time playback rate.
- **Recursive geometric fractal: expanded reactivity design not yet built** — see §6 for context. Decided design: shape count, sides-reactivity, rotation-reactivity, and drift as four independent, freely-combinable per-layer settings (not exclusive modes — nothing prevents a shape from rotating and increasing sides at once), with a dynamic cap on shape count that tightens specifically when sides-reactivity is enabled, since `shape_count × side_count` is the real cost driver, not either dimension alone. Rotation and drift don't add polygon complexity and don't factor into the cap. Growing/shrinking scale-based reactivity was considered and dropped as visually uninteresting relative to the other options. Deferred to milestone 8: this combination space needs interactive sliders to tune (both the cap's exact values and how the toggles feel combined) rather than more debug-tool keybindings.
- **Mandelbrot/Julia: screen-space rotation center** — see §6 for the full description and why it's a genuinely separate, bigger piece of work than the Julia-parameter-space version that already shipped.
- **Visuals don't correctly go idle on a silent source switch** — switching from file playback to an external loopback source that's currently silent (playing nothing) results in Particles continuing to spawn, Flow Fields continuing to animate, and some Radial/Spectrum bars getting visually stuck rather than settling to an idle state. Observed during milestone 6 testing; not investigated — no root cause identified yet, no fix attempted. Likely worth checking against the `band_idle`/idle-gate mechanism (§4) and the `ProducerHost` source-switch path (§3) as starting points whenever this gets picked up, given both are the most recent, most relevant mechanisms touching this exact seam, but that's a guess, not a diagnosis.
- **Spectrum `GlobalBeat` mode pulses per-band, not as one shared flash** — see §6 for the full description; not broken, just worth knowing if a single synchronized flash is ever wanted instead.

### Cross-platform (future, deferred until that push begins)

No macOS hardware is available locally. Linux testing can be set up directly, but macOS will need one of: CI runners (e.g. GitHub Actions macOS runners) for scripted build/test, a cloud Mac rental (MacStadium, AWS EC2 Mac instances) for interactive/visual spot-checks, or borrowed hardware for the human-review-required checks in `TESTING.md`. Running macOS in a VM on non-Apple hardware is not an option (violates Apple's EULA). This needs a decision before macOS implementation work starts, not after.
