# CLAUDE.md — Music Visualizer

Project-specific guidance for Claude Code. See `visualizer-design-spec.md` in the repo root for full architecture rationale — this file is the condensed, actionable version for day-to-day work.

## What this project is

A real-time, layered audio-reactive visualizer. Audio comes from local files or system audio loopback (not direct YouTube/Bandcamp stream extraction — that's explicitly out of scope, see spec §3). Visuals are independent modules composited into a stack the user can reorder, blend, tint, and duplicate. The app is two separate native windows: a WebView2 control panel for managing the layer stack and theme, and a raylib window rendering the composited visuals, with a fullscreen mode for the latter. See spec §7 for the full UI architecture.

## Stack

- C++17 for the audio/visual core
- miniaudio for audio I/O and loopback capture (WASAPI / Core Audio taps / PipeWire-PulseAudio monitor)
- raylib for rendering
- WebView2 (HTML/CSS/JS) for the control panel UI — a deliberate exception to "one language" for the core; see spec §7 for why and the `UIHost` interface that contains it

Don't introduce other audio or rendering libraries without discussing it first, and don't let the WebView2/JS side grow beyond the control panel (e.g., don't move visual rendering or audio logic into it) — the audio/visual core stays single-language with no FFI boundaries within it.

## Target Platform

**Windows is the primary target — for both the audio core and the UI.** Develop, build, and run natively on Windows (MSVC + WebView2), not through WSL2. The spec's macOS/Linux loopback paths and any future non-Windows UI host (WebKitGTK, WKWebView) remain documented for future portability but are not implemented or tested until Windows is solid. Both platform-facing boundaries — the audio producer interface and the `UIHost` interface — are designed to be swappable later; neither is implemented for anything but Windows now.

WSL2 is available and may be used for occasional diagnostic tooling (see `TESTING.md`'s concurrency section) but is not the dev/build/run environment.

## Architecture invariants — do not violate these

1. **Audio thread never blocks.** The miniaudio callback (file decode or loopback) only pushes PCM into a ring buffer. FFT/feature extraction happens on a separate worker thread, signaled via fixed-interval polling (interval bounded by the smallest expected FFT window/hop size, spec §3). The render thread reads the latest computed `AudioFeatures` snapshot via **triple buffering**, not a bare 2-slot double-buffer swap: three preallocated `AudioFeatures`, worker exclusively owns a private back slot, render exclusively owns a private front slot, and the shared middle slot's index + new-data flag are packed into one atomic word, claimed via a **compare-exchange retry loop** on the consumer side — not a blind atomic exchange, which was tried and itself had a regression (spec §4 has the full two-iteration history). A 2-slot index/pointer swap was tried before that and found to have a genuine data race — an unbounded-frequency, never-blocking writer can wrap back into the buffer a multi-statement reader is still mid-read of — see spec §4 for the fuller writeup. Don't revert to 2-slot double-buffering or a blind-exchange triple-buffer; both are known-bad. The ring buffer's overflow policy is overwrite-oldest, not reject-new — see spec §3 for the tradeoff reasoning and the discontinuity-flag mitigation for onset detection. Don't switch this to reject-new without discussing it — it was a deliberate choice, not a default. **Ring buffer capacity must be a power of two** (cheap bitmask wraparound, only debug-asserted — silently trusted in release) — don't construct it with a non-power-of-two size. **Lifetime, not currently type-enforced:** the ring buffer must outlive any producer's `stop()` call, and both the ring buffer and the `AudioFeatures` snapshot must outlive `FeatureWorker` — get construction/destruction order wrong in `app.cpp` and the failure is a use-after-free, not a caught error. If you're adding code to the audio callback path, stop and check which thread you're actually in.
2. **Visual modules never touch raw PCM or FFT bins directly.** They consume the shared `AudioFeatures` struct (banded energies, onsets, RMS, peak freq, waveform snapshot) filtered to their assigned frequency range if applicable. This is the contract that keeps layers interchangeable.
3. **Global beat is not a separate detector.** It's band index `kGlobalBandIndex` (16, the last slot after 16 log-scaled bands, `kTotalBands = 17` — spec §4), computed with the same per-band spectral-flux onset logic as every other band, just scoped to full-spectrum energy. Don't add a second beat-detection algorithm, and don't change the band count or global-band position without discussing it — both are fixed decisions, not defaults.
4. **Layers render to their own offscreen texture, cleared to transparent (alpha 0), not opaque black.** The compositor stacks textures; layers never share a canvas or render order-dependent state into each other directly. An opaque background silently breaks every blend mode except normal (additive/multiply/screen all depend on real transparency) — found as a real bug in milestone 3 when milestone 2's visual modules needed correcting. This applies to every visual module, present and future — see spec §5/§6. **Tint is compositor-only, applied once as a multiply after a visual's `render()` — visual modules never see `tint_color`.** Because multiply can only ever produce a result ≤ the tint color, full tint is a ceiling, not a floor: nothing a visual module draws pre-tint can appear brighter than the layer's own tint. An onset/pulse-style brighten effect must dim toward that ceiling and decay back up to it, not attempt to exceed it (see spec §6's Spectrum onset-pulse mechanism for the resolved version). If a visual module genuinely needs internal color control beyond this, that's what palette override (spec §5, currently unbuilt) is for — don't reach back into tint internals as a one-off exception for a single visual module. This cost real implementation rework once already; don't rediscover it. **The layer stack is capped at 32 (`Compositor::kMaxLayers`), enforced by `add_layer`/`duplicate_layer` returning `std::optional`.** Originally 16 (one per band + global, chosen semantically, not from measured performance), raised to 32 after repeated real runs via the debug tool's batch-generation feature (`-n` flag) across a variety of audio inputs — confirmed functionally stable at 32 with only 3 visual modules built (Waveform, Spectrum, Radial). This is not a performance-tested ceiling for the full module set: Particles, fractals, flow fields, and geometric will each add their own per-layer render cost once built, and 32 hasn't been checked under that load. Re-verify (ideally with real frame-time/GPU measurement, not just functional smoke-testing) once more modules exist, rather than assuming 32 still holds once the module count grows. **`resize()` on a visual module or the compositor requires a live GL context** — it allocates/resizes GPU render targets. `Compositor::add_layer` must call a new layer's `resize()` before that layer is usable; calling `resize()` (directly or via `add_layer`) without a live context is undefined behavior, not a caught error.
5. **Producers are interchangeable.** Local file playback and loopback capture both feed the same `push_frames(samples, count, channels, sample_rate)` interface. Don't special-case one producer downstream of that boundary.
6. **The control panel and visualizer are separate windows with no shared-surface compositing.** Don't build anything that requires the WebView2 panel to render through/over a live view of the raylib output (or vice versa) — that would require DirectComposition/shared-surface interop we've deliberately avoided. Each window renders against its own background. See spec §7.
7. **UI state crosses the C++/JS boundary through the defined state bridge only**, using the same JSON shape as layer preset persistence. Don't add ad hoc message formats or a second serialization scheme for UI state. Layer presets (saved layer-stack configurations) and themes (built-in UI skins) are distinct concepts with distinct storage — don't conflate them.
8. **The control panel's security defaults are required, not optional hardening.** Restricted navigation, a CSP scoping resources to local content, DevTools disabled in release builds, and scoped local file access all ship as part of building the panel (milestone 8) — not added later as a follow-up. See spec §7 and `TESTING.md`'s Security / adversarial input section.

## Build Order

Follow the milestones in spec §8 unless directed otherwise: local playback + feature extraction → first visuals → compositor → duplication + freq mapping → loopback capture → remaining visual modules → tint/palette → control panel UI. Each is a checkpoint with its own completion bar — see `TESTING.md`'s milestone completion checklist before considering one finished.

Don't jump ahead to later-stage visuals (fractals, flow fields, particles), loopback capture, or the control panel UI until the compositor and layer stack are working — retrofitting compositing onto a single-visual renderer, or building UI against a layer model that's still changing shape, is the mistake this order is designed to avoid.

## Verification

See `TESTING.md` for the full verification strategy. Short version: pure-logic pieces (FFT banding, onset detection, envelope smoothing, serialization) get unit tests and synthetic fixtures. Visual, audio, and control-panel UI correctness are all verified by a human reviewing the actual running app — not by an agent claiming a rendered frame, clean buffer stats, or "it compiles" means it works. File parsing and the WebView2/JS boundary additionally get adversarial-input coverage (malformed fixtures, state-bridge validation) since those are real trust boundaries even in an offline app. Read `TESTING.md` before deciding how to verify a change.

## Implementation Guidelines

- Prioritize performance where there's a choice between approaches. If a performance-favoring approach costs functionality or scope, don't drop that functionality silently — surface the tradeoff and reason about it before proceeding.
- Don't edit design documents (`visualizer-design-spec.md`, this file) as a side effect of implementation work. These are updated only when explicitly asked. If implementation reveals the docs are wrong or out of date, flag it instead of fixing it inline. **This restriction is about who authors changes to these docs, not about version control.** Once a doc has been updated (whether by explicit request or delivered as ready-to-use content), commit it like any other tracked file — these docs are committed source of truth per `STRUCTURE.md`'s tree, not local-only or excluded from git. Don't withhold `CLAUDE.md` or any other core doc from a commit on the theory that "can't edit it" means "can't commit it" — they're different things.
- Check the relevant section of `visualizer-design-spec.md` (and this file) before making architectural or structural changes — implementation should follow the spec, not drift from it. If a task isn't covered by the spec, that's a design decision to surface, not one to improvise.
- Favor idiomatic C++/miniaudio/raylib solutions over clever or unusual ones. Idiomatic here means: what a competent C++ developer familiar with these libraries would recognize immediately, not necessarily the most concise or performant possible construct.
- **No comments in source code, anywhere, of any kind — no exceptions.** Not for formulas, not for algorithms, not for opaque values, not for gotchas, not for invariants, however true or however much it would help a future reader. Every prior version of this rule (what-not-why, a necessity test, an accuracy-over-brevity carve-out) was judgment-based and every version was violated in practice, repeatedly, despite the judgment call being explained clearly each time — the specific, recurring failure was optimistic self-assessment of whether a given comment passed the test, not confusion about what the test said. A rule with no judgment call in it removes that failure mode structurally rather than asking for better judgment next time. If a piece of code is genuinely opaque, that's a signal to improve the name, not to write a comment about it. If a real architectural constraint or invariant needs to be preserved for future code to follow, flag it for review — it belongs in `visualizer-design-spec.md` (which already documents this project's real decisions and bug fixes at length) when explicitly added, never written into the spec unilaterally and never left as a comment, however short.
- **This is mechanically enforced, not self-reported.** Any review of a unit of work (the test/audit agent's process, or a dedicated pass) checks the actual diff for comment syntax (`//`, `/* */`) — a claim that no comments were added is not sufficient on its own; the diff itself is checked. See `TESTING.md`.

## Working style

- Give clear reasoning for tradeoffs rather than just stating a conclusion.
- Never make a design decision unilaterally. When there's a real choice — not just an implementation detail — surface the options and the tradeoffs and wait for a decision before proceeding.
- Keep platform-specific code (WASAPI/Core Audio/PipeWire) isolated behind the shared capture interface — don't let platform branches leak into feature extraction, compositor, or visual module code.
- No placeholder/stub visuals presented as done — if a visual module isn't fully wired to `AudioFeatures`, say so explicitly rather than leaving silent TODOs.
- Same principle applies to environment failures: if something can't be initialized, say so plainly rather than quietly stubbing out the affected system or fabricating success. (No-hardware fallback behavior no longer applies to this project — see `TESTING.md`.)

## Compact Instructions

If context compaction happens mid-session, prioritize preserving, in this order:

1. **The specific unresolved question or bug currently being investigated** — what's been ruled in/out so far, what the next diagnostic step was going to be, and any concrete data already gathered (specific values, specific file/timestamp references, specific test results) that led to the current hypothesis. This is the state most likely to be expensive to reconstruct and least likely to already be written down anywhere else.
2. **Any decision that's been reasoned through and settled in this session but not yet written into `visualizer-design-spec.md`, `CLAUDE.md`, `STRUCTURE.md`, or `TESTING.md`.** Settled facts already committed to those docs don't need to be preserved in the summary — they're safely persisted and will be re-read at the start of the next session. It's the gap between "decided" and "documented" that's actually at risk.
3. **Rejected approaches and why**, specifically for whatever's currently being worked on — not a general log of every alternative ever considered, but enough to avoid re-proposing something that was already tried and found wanting in this session.

Lower priority, safe to compress heavily or drop: verbose tool output, full file contents already reflected in the current state of the repo, and narration of process/steps taken to arrive at something now already settled and documented.

If a natural stopping point is reached before compaction is forced, prefer writing settled decisions into the actual docs over relying on compaction to carry them forward — see `STRUCTURE.md`'s note that these files are the durable record, not conversation history.
